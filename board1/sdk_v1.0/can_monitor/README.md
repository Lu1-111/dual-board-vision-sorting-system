## 物理连接与通信参数

先根据板卡原理图/丝印确认 CAN0 对应端子，再连接 CAN_H、CAN_L 和参考地。两端应各有一个 120Ω 终端电阻；先确认板载电阻/跳线是否已经接入，避免重复增加。断电测量总线 H-L 时，两端各 120Ω 的并联结果约为 60Ω。当前未根据图片确认端子排具体脚位，不能按猜测接线。

两块板使用相同名义速率 500 kbit/s。本 BSP 的 CAN FD 控制器启动需要有效的数据段时序，所以设置 `dbitrate 2000000 fd on`；应用发送的仍是**标准 ID、8 字节经典 CAN 帧**，没有发送 FD 帧或开启帧内速率切换。配置脚本显式区分 `loopback` 和 `physical`。

第一块板先运行模拟发送：

```sh
/opt/can-monitor/setup_can.sh physical can0
/opt/can-monitor/can_sender --can can0 --demo
```

第二块板切换为 `can` 模式。即使真实线缆连接成功，第一块板使用 `--demo` 时，UI 仍标识为“发送端使用模拟数据”。应进一步实测拔线/恢复、两端重启、告警确认，并核对 CAN 错误计数，再接真实视觉结果。

内部回环只证明控制器与软件收发通路可用；2026-10-27 已另外完成两块板的实线双向验证。

## 真实视觉结果接入

不需要先训练视觉模型即可完成 CAN 联调。后续视觉/控制程序每秒至少一次，以“写临时文件后重命名”的方式更新 `/run/line-state.txt`，包含以下 11 个十进制整数：

```text
运行状态 机械臂状态 视觉状态 当前类别 置信度 红计数 黄计数 蓝计数 绿好计数 绿缺陷计数 告警位图
```

例如 `1 0 1 1 95 12 8 6 3 0 0` 表示运行中、臂空闲、视觉正常、红色、95%、五类计数分别为 12/8/6/3/0、无告警。

```sh
/opt/can-monitor/can_sender --can can0 --state /run/line-state.txt
```

文件不存在、格式错误、字段越界，或超过 3 秒没有更新时，发送端停止发送心跳，监控端随后超时，避免旧文件持续伪装成正常采集。它只读取状态文件，不直接操作视觉模型或电机。不能同时运行 `--demo` 和 `--state`。类别目前是演示约定，最终训练类别确定后两端需一致调整。

## 协议 v1

标准 11 位 CAN ID，DLC 必须为 8；多字节整数为小端。每个发送周期先发会话，再发心跳、状态、5 个计数和最多 3 个最新告警快照。默认周期 500ms；接收端使用单调时钟，3 秒无新心跳视为超时。设备日期未校准不会破坏心跳超时判定。

| ID | 方向 | 8 字节负载 |
|---|---|---|
| `0x100` | 板1→板2 | B0=版本1，B1=是否模拟(0/1)，B2..3=0，B4..7=非零32位会话号 |
| `0x101` | 板1→板2 | B0=1，B1=8位循环序号，B2=运行状态，B3=活跃告警数0..3，B4..7=运行秒数 |
| `0x102` | 板1→板2 | B0=1，B1=同周期序号，B2=运行状态，B3=臂状态，B4=视觉状态，B5=类别，B6=置信度0..100，B7=0 |
| `0x110`..`0x114` | 板1→板2 | B0=1，B1=同周期序号，B2..3=0，B4..7=32位累计计数，依次对应五类 |
| `0x120` | 板1→板2 | B0..3=32位非零事件号，B4高4位=告警类型、低4位=类别，B5=活跃0/1，B6..7=持续秒数(上限65535) |
| `0x220` | 板2→板1 | 原样回显已接收告警的8字节负载，仅表示接收确认 |

运行状态：0待机、1运行、2暂停、3故障。臂状态：0空闲、1运动、2故障。视觉状态：0关闭、1正常、2降级、3故障。类别：0无、1红、2黄、3蓝、4绿完好、5绿缺陷；无物料时置信度必须为0。告警类型：1颜色不符、2物料滞留、3缺料；状态文件的位图对应 bit0..2。

计数必须收齐同一心跳周期的五帧才更新，缺帧不混用上个周期。未知 ID、长度错误、版本错误、字段越界、RTR/扩展帧不会更新业务状态。同一事件重复上报不重复插入；恢复后收到旧活跃快照不会重新激活事件。源会话改变时清空本会话 UI 历史，防止重启后事件号复用串联。

每类告警保留最新事件快照，发生、持续、恢复均重复发送；接收端重启或单次丢包后可恢复最新状态。此版本不是可靠历史消息队列：长时间掉线期间发生并结束的中间事件可能丢失，只能补回每类最新事件；UI 历史也未持久化。恢复时刻取接收端估算值，不是精确的板1现场时间。若新的同类事件证明旧事件已结束，但旧恢复消息缺失，标为“结束时间未知”。

会话号用于区分发送进程重启，不是身份认证；当前只允许一个板1发送端。不要在实线模式同时运行多个模拟发送器。

## BSP 实测问题及处理

1. 仅设置 `bitrate 500000` 时出现 `canfd_chip_start failed`；补齐数据段时序后两块板均能启动。对应本地 BSP `drivers/net/can/ipms_canfd.c` 的数据段参数校验。本次不修改内核/设备树/HDMI。
2. BSP 的 `ipms_canfd.c` 强制使用单个 PTB，发送路径未启用队列停止，且在提交时就累加 TX 统计；短时间连续提交可能覆盖尚未完成的帧。控制板发送程序保留每帧 2ms 间隔；监控板现将告警确认排队，以 Qt 单次定时器每隔至少 5ms 提交一帧。发送失败保留队首重试，队列最多 64 条、保留不超过 3 秒，换会话或接口异常时清空旧确认。诊断栏显示待确认、发送失败和过期数量。
3. 上述修复在应用层规避已发现的驱动发送问题，没有修改内核；只针对当前低频监控负载验收。周期快照仍保留，接口 TX 计数不能代替对端逐帧接收验证。

## 外部模型说明（本轮仅说明）

可使用正常云端大模型 API，无需限定小模型。模型在服务商服务器运行，第二块板只发请求和显示结果。只有在板内本地推理才受内存/NPU能力约束。HTTPS 调用还需系统时间、证书和网络通畅；不能通过关闭证书校验来代替正确配置。

调用云端 API 需要互联网，但不要求网线连接电脑：板子可直接联网，也可由联网电脑中转。现有调试串口不会自动共享网络。板子的无线驱动/固件和 USB 网络共享尚待实测，不承诺插上就能联网。当前没有路由器和电脑网口，后续再选择可行的联网方案，本轮未修改网络设置或购买设备。

第一版可发送结构化异常数据给普通文本模型生成“可能原因和排查建议”；有限信号不能支持确定性的机械故障结论。若需要看图，需图像输入 API，并另建图像传输通道，不能把整张图片直接塞进一个 CAN 帧。尚未选供应商、未配置密钥、未调用收费服务。

# 运行状态与告警分离（2026-10-25 修正）

`--demo` 中颜色不符、物料滞留、缺料只产生视觉告警，生产线运行字段保持“运行中”。视觉异常不等于控制器确认的停机或故障；缺料可对应空转，物料滞留也不能仅凭单张照片断言整条线停机。颜色不符期间继续累加不合格物料计数。

真实 `--state` 模式仍原样发送独立的运行字段：0待机、1运行、2暂停、3故障，不根据告警位图覆盖。运行状态应来自控制板实际控制状态。监控页面切换、图片查看和AI分析不发送运行控制命令。
